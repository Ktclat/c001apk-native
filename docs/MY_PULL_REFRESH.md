# My aggregate pull-to-refresh candidate

Source base: `f8bbd5627db82efc3e3f77d9dc5c830a6fae7556`. Behavioral reference: Flutter `apps/flutter/lib/pages/message/message_page.dart` refreshes the own profile and notification counts together. This bounded increment is not a full Flutter parity claim.

## Behavior

- Pull down past the standard Material 3 threshold at the top of My to request one profile read and one notification-count read. Ordinary scrolling remains the existing `ScrollState`; scrollable header, bottom safe-area/dock padding, 48dp controls and floating-dock recovery are retained. Uses the already pinned Material3 1.3.1 pull-refresh modifier and indicator; no dependency changes.
- The scroll container exposes a separate `刷新个人资料和未读数量` accessibility action when an aggregate refresh can begin. The existing `显示底部导航` action is retained on the same node. Header refresh still reloads only the profile; count retry still reloads only counts.
- An aggregate refresh is admitted only while resumed and neither resource is in flight. Both slots are reserved synchronously, so repeated gestures or accessibility invocations do not queue parallel reads. Initial entry does not double-load. The indicator ends when both independent reads finish, including partial failure/cancellation; successful content does not wait for or depend on the other result.
- Both requests are scoped to account UID/generation and repository identity. They use the unchanged authenticated-session/strict-cookie-revision repositories. Guest, needs-login and recovery states do not issue either read or expose aggregate refresh. No mutable global account lookup was introduced.
- Pause/disposal cancels reads; post-await cancellation checks reject late/uncooperative responses, failures and exceptions. Counts reload once per resume. A completed profile remains independent and does not refetch solely on resume; an interrupted profile retries on resume. Manual same-generation revision cancellation becomes an explicit retryable error rather than stuck loading.
- Same-owner refresh retains the previous successful profile/avatar/stats and count badges while the new reads are in flight. It does not insert loading cards over existing success, so aggregate progress is an overlay rather than a content jump. Initial/no-success loads remain explicit. Failure or cancellation replaces the affected success with an explicit error (counts become unknown, not stale current badges). Owner/repository replacement never inherits retained values; interrupted reads are retried on resume.
- No durable cache, polling, write endpoint, read acknowledgement or unread clearing is added. Dock hide/default behavior, routing and API decoding are unchanged.
