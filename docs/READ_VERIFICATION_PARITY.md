# Read verification parity (candidate; validation pending)

## Evidence and source contract

Fresh actual NativeApp synthetic baseline frames from `native-ui-audit-20261025` show a supported `err_request_captcha_v2` Home rejection with only a generic message and Retry for both guest and account. Controlled loopback detail baselines show guest has no verification action while authenticated graphic detail already does. These are synthetic rendered components, not a physical device or live-service CAPTCHA result.

Flutter source comparison: `logic/network/request.dart`, `captcha_challenge.dart`, and `pages/webview/captcha_page.dart` in `flutter-ci-memory-fix/apps/flutter` recognize the exact v2 marker and use a local HTML provider-SDK host. The proof returns from its callback as `NEC:<id-prefix>:<proof>` and is attached to the indicated proof field, or the `validate` cookie for an explicitly blank field. No arbitrary challenge-URL navigation contract was found. Flutter's Dio `get` has no non-2xx verification catch, so this document does **not** claim Flutter verifies all HTTP 403 responses.

## Implementation

- Home/list/comment reads and feed-detail recovery retain a supported challenge as a `PendingRead<T>` capability instead of dropping it in the repository or ViewModel. A visible **亲自完成验证** action opens the actual dedicated provider-SDK WebView. Graphic CAPTCHA uses the existing typed-input image UI.
- Read-only HTTP 4xx responses are bounded and inspected for actual supported error envelopes. Bare403, HTML, success-shaped error bodies, redirect locations, unknown CAPTCHA hints, rate limiting, server errors, and risk-control without a supported challenge do not acquire a verification action. No challenge URLs are fabricated or followed.
- Completion returns to the original screen; it does not automatically read again. A second explicit **验证完成，重新读取…** gesture permits exactly one GET with unchanged original method, endpoint, target, query and cursor. A second challenge does not loop. Existing publicly readable detail content is retained if the verified read fails.
- Reads support the explicit blank validate-cookie protocol and Flutter-valid underscore proof fields, except normalized collisions with original query/form keys or protected identity/auth/device/session/signature/route controls. Nonblank proof is only an added query value on the captured GET, never a header or arbitrary cookie; it is not cached for later reads. Mutation challenges retain their separate authenticated flow.
- Captured account/guest owner, generation, device, and cookie revision must remain current. The AccountStore read predicate compares them under one monitor. Route departure, refresh/replacement, reply invalidation, eviction, cancellation, and five-minute expiry invalidate capabilities.
- A private per-read overlay can accept only API `SESSID` cookies, never `uid`, `token`, `validate`, or account credentials. It does not write the vault or promote guest to an account. The pending continuation and its private overlay are closed after the one explicit retry. Only after a successfully decoded verified read may a separate, read-only in-memory cache retain the accepted SESSID and (blank-field protocol only) encoded validate cookie for later public API GETs. Query-field proofs are never cached. Reuse is bounded to 24 hours maximum, earlier SESSID expiry, and exact owner/generation/device/raw-cookie revision. Server SESSID rotation/deletion clears validation without extending lifetime. Any subsequent CAPTCHA, account/session change or expiry invalidates accepted validation; exact capture-version compare-and-set prevents stale responses from overwriting newer state. This intentionally does not match Flutter disk persistence and is never supplied to login/social/personal-account request factories, public-share readers or WebView cookies.
- The fixed local HTML host now supplies the same base and history URL. The callback retains its exact local-URL check rather than accepting `null`/`about:blank`. Android documents the separate history URL; Chromium `AwContents.fixupHistory` maps null to `about:blank` before `LoadUrlParams` uses it as the virtual URL. This mismatch was exposed by the real production callback fixture, not patched around with test-side URL spoofing. Sources: [Android WebView API](https://developer.android.com/reference/android/webkit/WebView#loadDataWithBaseURL(java.lang.String,java.lang.String,java.lang.String,java.lang.String,java.lang.String)), [Chromium AwContents](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/android_webview/java/src/org/chromium/android_webview/AwContents.java).
- The SDK host imports no Coolapk cookies from `CookieManager`, injects no account cookies, disallows Coolapk resource origins, and exposes only the existing nonce-bound proof callback. No global cookie clearing is performed. Vendor resources remain allowlisted. The provider loader 2.5.4 audio implementation uses Blob/direct Audio, so CSP permits only blob media and the same existing HTTPS provider suffixes; it does not add arbitrary media origins or unsafe-eval. This does not claim a real provider session was exercised in Robolectric.

## Validation scope

`ReadSessionMemoryTest` covers accepted next-read reuse, 24-hour non-sliding lifetime, SESSID expiry/rotation/deletion, revision/account/device/generation changes, ownerless non-retention, and stale concurrent publish/revoke/rotation. `ReadVerificationRepositoryTest` uses explicit MockWebServer endpoints for all API and public-share reads; identities, cookies, and proofs are synthetic. `ReadVerificationViewModelTest` covers route/capability ownership and invalidation. `ReadVerificationNativeAppTest` uses actual NativeApp/repository/VM/verification components with loopback API/share responses and a hard external-DNS deny. ShadowWebView records the production loadData/JS interface without downloading or running provider JavaScript. A synthetic test callback exercises return handling; it is not CAPTCHA solving or a live-service success.

The UI suite captures guest/account Home/detail entry, visible host, cancel, proof-return with explicit retry, and synthetic read-success states. It also asserts host identity survives recomposition, old callbacks are ignored, WebViews/interfaces are destroyed on close, no global account cookies leak into guest reads, and only one explicit retry is dispatched. Exact output paths, hashes, test counts, screenshots inspected, independent review, and final aggregate/build results must be supplied by the coordinator after execution. Until then this remains a candidate, not a passed build or full parity claim.

Independent SDK host source review compared exact Flutter invocation and public loader 2.5.4. A real-browser SDK-load smoke could not reach the locally hosted exact production fixture because cloud browser localhost is isolated (connection refused after bounded retry); no provider runtime-load or real-service completion is claimed.
