## Bounded full-body increment

Ordinary feed-detail `message` is retained separately from the existing 12,000 UTF-16-unit list/history/favorites preview, with raw and decoded body limits of 262,144 UTF-16 units. The reader displays one explicit 4,000-unit segment at a time; user page changes reveal the new page's start. Bounded parsing/page preparation runs off Main and guarded publication occurs on Main. Unsupported structured articles, inline media or parse/limit failures are explicit, with a separate browser-original action; no unsupported body is silently declared complete.

Shared JSON preflight limits depth to 64 and lexical nodes to 20,000, inside the existing 4 MiB response-byte cap. A single captured ordinary-read session is used without AccountStore changes; normal guest/authenticated response Set-Cookie handling remains allowed under existing browse semantics. This is not a new revision-current read contract or an aggregate-memory/performance guarantee.

Build65 covers parent list → detail → Back restoration and reviewed first-page, final-tail, unsupported-article and browser-error frames; Build66 passed the coherent gate. Child-return retention is now implemented in the bounded increment below, not retroactively covered by that baseline. Structured article blocks, inline-media layout and continuous full-text selection remain gaps; no durable process-restoration or full Flutter parity is claimed.

## Bounded reader child-return increment

At most **13 memory-only, latest-per-feed bookmarks** carry account/generation/feed ownership, an exact UTF-16 body digest, bounded segment/list position and stable reply anchors. Parsed readiness precedes the first restored measurement; actual-root child → Back tests retain segment, positive scroll and geometry without corrective scrolling. Repeated A → B → A routes use each feed's latest position, not a per-visit snapshot, without rewriting navigation. Restore/commit checks require the current owner, cached body and route; stale, abandoned or departed work cannot republish a bookmark.

Equal-body metadata refresh preserves position. Changed/unsupported bodies and lost ownership reset; genuinely evicted body data loses its bookmark and uses normal refetch on return. A fresh owner/process has no durable bookmark and starts over after genuine loading; synthetic fresh-owner checks are not a physical process-kill test. No body, ParsedPost or bitmap enters saved state. Font, viewport or reply changes have no exact geometry guarantee; missing/mismatching reply anchors reset safely. Valid feed IDs over 256 UTF-16 units remain readable without retention. The 13-entry bookmark limit is not a global application-memory cap.
